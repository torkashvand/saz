# CLAUDE.md — Saz Repository Development Guide

## 1. Purpose

This file defines how automated coding sessions should work in this repository.

Saz is a safe, auditable workflow execution platform for operational automation. Changes must preserve reliability, security, testability, and operator trust.

The repository contains:

- `backend/`: Python 3.12+, FastAPI, SQLAlchemy, Pydantic, APScheduler, LiteLLM, Alembic, pytest
- `frontend/`: Next.js 14, React, TypeScript, TanStack React Query, Tailwind CSS, Vitest

Safety, auditability, policy enforcement, retry correctness, callback handling, and test coverage are core product requirements.

---

## 2. Core Working Rules

### Read before editing

Before changing code:

1. Identify the exact scope.
2. Read the relevant source files.
3. Read nearby tests.
4. Trace the full path, not only the local function.

For backend work, trace:

```text
route → schema → service → repository → model/unit of work → executor/tool/policy → audit event → API response
```

For frontend work, trace:

```text
page/component → hook → API client → type → backend contract → UI state
```

Do not patch based only on filenames or assumptions.

### Keep changes small

Prefer small, reviewable changes.

Do not:

- rewrite unrelated code
- rename broad concepts without need
- introduce new abstractions without a clear bug or requirement
- mix refactoring with feature work unless necessary
- change public contracts without updating all consumers

### Preserve existing structure

Use the current project layout unless there is a strong reason to change it.

Respect existing patterns for:

- backend services
- repositories
- unit of work
- API schemas
- test fixtures
- frontend hooks
- frontend components
- UI types
- error handling
- audit event flow

If a pattern is unsafe or broken, first add a regression test that exposes the issue.

## 3. Commit and PR Rules

### No AI attribution in commits

Do not include any AI-related attribution in commit messages, PR titles, PR descriptions, code comments, or generated files.

Do not write:

- `Generated by Claude`
- `Generated with AI`
- `AI-assisted`
- `Claude changes`
- `Co-authored-by: Claude`
- `Co-authored-by: AI`
- any similar attribution

The repository history should describe the engineering change, not the tool used to create it.

### Commit messages

Keep commit messages short, clear, and useful.

Preferred format:

```text
<type>(<scope>): <short action>
```

Examples:

```text
fix(api): validate flow registration
test(engine): cover webhook reject state
feat(runs): expose retry attempt metadata
refactor(policy): simplify PII decision path
docs: update workflow testing guide
```

Rules:

- Use the imperative mood.
- Keep the subject concise.
- Avoid long, story-like commit messages.
- Avoid vague subjects like `fix stuff`, `updates`, `changes`.
- Do not mention internal coding sessions or tools.
- Do not include large bullet lists in commit messages unless explicitly requested.

### PR discipline

A PR should have:

- clear scope
- linked issue or reason
- tests added or updated
- migration notes if relevant
- API/frontend contract notes if relevant
- screenshots only for visible UI changes
- known limitations if any

Do not hide behavior changes inside refactors.

## 4. Test-First Development

Testing is mandatory for meaningful changes.

### Default rule

Every code change must include tests unless it is clearly documentation-only, formatting-only, or a trivial comment correction.

For bug fixes:

1. Add a failing regression test first.
2. Fix the minimum production code needed.
3. Keep the regression test.
4. Run the relevant test subset.
5. Run broader tests when feasible.

For new behavior:

1. Write tests for the expected contract.
2. Implement the behavior.
3. Add negative and edge cases.
4. Verify API and UI contracts if applicable.

### Do not rely on happy paths only

For every important feature, cover:

- success path
- validation failure
- runtime failure
- retry/recovery behavior
- unauthorized or unsafe input where relevant
- database state after failure
- emitted audit events
- side effects that must not happen

### Tests must prove behavior

Avoid tests that only assert implementation details.

Good tests verify:

- persisted DB state
- API response contract
- step/run status transitions
- audit event emission and persistence
- tool execution or non-execution
- policy blocking behavior
- error shape
- retry attempt numbering
- callback idempotency
- frontend visible behavior

Weak tests only verify:

- a mock was called
- a helper returns a trivial value
- a component rendered without checking useful output
- a status code without response semantics
- a snapshot without meaningful assertions

## 5. Backend Testing Standards

Backend tests use pytest.

### Test database

Tests run against PostgreSQL only — there is no SQLite fallback. `conftest.py`
creates one isolated database per pytest-xdist worker from `TEST_DATABASE_URL`
(default `postgresql+psycopg2://saz:saz@localhost:5433/saz_test`; CI runs a
`postgres:16` service on `:5432`) and truncates + reseeds the canonical test
user before each test. A reachable PostgreSQL cluster is required to run the
suite locally.

Because foreign keys are enforced (unlike the old SQLite setup), tests that
insert `events`, `runs`, or `steps` must seed their parent rows — use the
`seed_run(engine, run_id, step_ids=[...])` helper in `conftest.py`. Other
PostgreSQL realities to respect: datetimes come back timezone-aware (compare
against UTC-aware values, not naive); pass `engine.url.render_as_string(
hide_password=False)` to any background-thread engine (`str(url)` masks the
password and breaks auth).

### Test organization

Use the existing layout:

```text
backend/tests/unit/
backend/tests/services/
backend/tests/integration/
backend/tests/api/
backend/tests/contracts/
backend/tests/examples/
backend/tests/acceptance/
backend/tests/regression/
```

Use the most appropriate level:

| Level | Purpose |
|---|---|
| unit | Pure logic, compiler rules, validators, small policy functions |
| services | Business behavior around service boundaries |
| repository/database | persistence, transactions, model/query behavior |
| integration | executor/runtime behavior with realistic fakes |
| api | FastAPI request/response contracts |
| contracts | OpenAPI, DSL, audit event, schema contracts |
| examples | workflow YAML validity and drift protection |
| acceptance | operator-level flows across API/runtime/database/audit |

### Backend test style

- Use function-based tests.
- Use descriptive names.
- Prefer real models and real unit-of-work behavior where possible.
- Use fakes instead of deep mock chains.
- Avoid over-mocking `WorkflowExecutor`.
- Avoid tests that bypass the real runtime path when runtime behavior is the subject.
- Assert both final state and important intermediate side effects.

### Critical backend areas that require tests

Always add or update tests when touching:
    
- `saz/compiler/dsl.py`
- `saz/compiler/template_validator.py`
- `saz/agents/*`
- `saz/engine/executor.py`
- `saz/engine/scheduler.py`
- `saz/engine/suspension_sweeper.py`
- `saz/policies/*`
- `saz/audit/*`
- `saz/services/*`
- `saz/repositories/*`
- `saz/api/routes/*`
- `saz/tools/*`
- Alembic migrations
- run/step status transitions
- retry behavior
- human approval
- webhook callbacks
- credential handling
- PII handling
- audit/event behavior

### Required assertions for runtime changes

For workflow runtime changes, assert:

- `Run.status`
- `Step.status`
- `Step.attempt`
- `Step.output`
- `Step.error`
- `Run.error`
- audit events
- tool calls made or not made
- retry behavior
- callback behavior
- database state after failure

### Required assertions for safety changes

For policy, verifier, PII, and credential changes, assert:

- unsafe tool calls do not execute
- sensitive values do not appear in API responses
- sensitive values do not appear in audit events
- errors are structured
- policy decisions are persisted or emitted where expected
- blocking does not leave stale running or suspended state

## 6. Frontend Testing Standards

Frontend tests use Vitest and React Testing Library.

Use existing locations:

```text
frontend/__tests__/runs/
frontend/__tests__/flows/
frontend/__tests__/setup.ts
```

When touching frontend behavior, test what the operator sees.

Cover:

- loading states
- error states
- run status display
- step status display
- retry/resume UI behavior
- callback panels
- approval panels
- React Query invalidation behavior
- WebSocket event overlay behavior
- API type contract assumptions
- form validation
- disabled/enabled action states

Do not only test helper functions if the bug can exist in page-level wiring.

## 7. Coverage Expectations

Coverage should be meaningful, not cosmetic.

### Minimum expectations

High-risk backend areas should have strong branch coverage:

- compiler and DSL validation
- workflow executor
- policies and PII handling
- verifier/critic paths
- callback and resume behavior
- retry behavior
- audit/event behavior
- API response contracts
- credential handling

### Coverage must include negative paths

Add tests for:

- malformed YAML
- invalid templates
- unknown tools
- unsupported step types
- invalid AI output schemas
- verifier fail/replan/escalate decisions
- policy blocking
- PII detection
- duplicate callbacks
- malformed callbacks
- retry after failure
- suspension timeout
- failed tool calls
- database rollback or consistency after failure

### Side-effect assertions

For blocked or failed flows, explicitly assert that forbidden side effects did not occur.

Examples:

- tool was not called
- artifact was not written
- credential was not exposed
- run was not marked completed
- suspended step was not left running
- callback was not processed twice

## 8. Backend Product Semantics

### Run lifecycle

Expected lifecycle:

```text
queued → running → suspended → queued/running → completed
queued → running → failed
queued → running → error
```

Important rules:

- `suspended` means execution has stopped at a wait point.
- No later step should execute while the run is suspended.
- Retry must preserve previous attempts.
- Resume must advance the suspended step or explicitly fail/cancel it.
- Failed runs must expose structured errors.
- Audit events must reflect meaningful state transitions.

### Retry semantics

Retry is same-run retry.

Rules:

- reuse the same `run_id`
- preserve historical step rows
- increment step attempt numbers
- restore completed step outputs
- restart from the failed step
- do not re-run completed steps unless explicitly intended
- emit/persist retry-related events where applicable

### Human approval semantics

Human approval must be explicit and auditable.

Tests should verify:

- run becomes suspended
- approval step becomes suspended
- later steps do not run before approval
- approval resumes execution
- rejection has clear run and step semantics
- approval/rejection reason is persisted where expected
- audit events are emitted

### Webhook callback semantics

Webhook callbacks must be safe and idempotent.

Tests should verify:

- callback ID exists
- valid callback resumes or rejects according to contract
- duplicate callback does not apply side effects twice
- malformed callback is rejected safely
- late callback after timeout is safe
- callback state is queryable without loading all runs into memory

### Error shape

Errors should remain structured dictionaries, not arbitrary strings.

Expected style:

```json
{
  "message": "...",
  "type": "...",
  "category": "...",
  "retryable": false
}
```

When changing error handling, check:

- `Run.error`
- `Step.error`
- `Run.error_summary`
- API detail response
- API list response
- audit event payloads
- frontend rendering

## 9. API and Contract Discipline

Backend/frontend contract changes must be complete.

When adding or changing an API field, update:

1. SQLAlchemy model if persisted
2. repository DTO
3. service logic
4. API schema
5. API route
6. frontend type
7. frontend API client usage
8. UI component rendering
9. tests

Do not create parallel fields for the same concept.

Do not leave legacy aliases unless explicitly needed and tested.

### API tests should verify contracts

For API route changes, assert:

- status code
- response shape
- important field values
- error payload shape
- persistence side effects
- authorization/validation behavior if relevant

Do not only assert `200`.

## 10. Database and Migration Rules

When changing database models:

- add or update Alembic migration
- verify migration matches SQLAlchemy model
- update repositories
- update DTOs and schemas
- update tests
- consider existing data compatibility
- avoid destructive migrations without explicit plan

Both the app and the test suite run on PostgreSQL (see section 5). Tests
exercise real foreign-key enforcement, JSON, and transaction semantics, so
verify JSON fields, callback lookup, constraints, and transaction behavior
against the actual PostgreSQL-backed tests.

## 11. Security and Secrets

Never expose secrets.

Do not log or return:

- API keys
- tokens
- passwords
- credential values
- secret template values
- raw sensitive payloads
- PII unless explicitly allowed and sanitized

When touching credential or PII code, check:

- API responses
- audit events
- telemetry
- error messages
- test output
- frontend displays

Use redaction and tokenization consistently.

---

## 12. AI / LLM Development Rules

Saz uses AI behavior, but runtime correctness must not depend on trust in model output.

When touching planner, AI ops, verifier, or critic code:

- validate model output with strict schemas
- reject unexpected fields when the contract says so
- test malformed JSON
- test schema-invalid JSON
- test missing required fields
- test enum violations
- test repair failure
- test verifier FAIL, REPLAN, ESCALATE, and PASS paths
- use fake LLM ports in tests
- do not call real LLMs in unit or integration tests

Prompts and validators must agree.

If a prompt says the model must not add extra fields, the validator must enforce that.

---

## 13. Tool Execution Rules

Tools can create real side effects. Treat them as high-risk.

When touching tools, test:

- success behavior
- validation failure
- timeout
- non-2xx HTTP behavior
- exception handling
- output shape
- audit event behavior
- retry behavior
- secret redaction
- no side effects when blocked

For external tools, use fakes in tests unless the test is explicitly marked as external/manual.

## 14. Multi-User Development Rules

This repository is developed by multiple people. Make changes easy to review and safe to merge.

### Avoid surprises

- Do not reformat unrelated files.
- Do not reorder large blocks without need.
- Do not change naming conventions casually.
- Do not remove behavior without tests proving it is unused or wrong.
- Do not introduce hidden global state.
- Do not make environment-specific assumptions.

## 15. Controlled String Values

Do not use plain `str` for values with a fixed set of allowed options.

Prefer `Literal` for small/local value sets:

```python
from typing import Literal

ApprovalAction = Literal["approve", "reject"]
ResumeStatus = Literal["resumed", "rejected", "error"]
```

Use `StrEnum` when the value is reused across modules, drives workflow/business logic, or represents a domain concept.

Rules:

- Do not document allowed values only in comments.
- Do not duplicate the same `Literal` union across many files; create a named alias.
- Keep free-text fields as `str`: `name`, `title`, `description`, `message`, IDs, URLs, paths.
- For Pydantic/API models, controlled values must be validated by the type.
- Prefer the smallest clear type; do not create an enum when a local `Literal` is enough.

### Keep compatibility in mind

Before changing a contract, check:

- backend API users
- frontend types and components
- stored workflow YAML examples
- tests
- documentation
- migrations
- existing database records

### Comments and documentation

Comments should explain why, not narrate what the code already says.

Remove stale comments.

Do not add speculative comments about future work unless they are linked to a concrete TODO or issue.

## 15. Session Performance Rules

Automated coding sessions should be focused and efficient.

### Before editing

- Use search tools to locate exact files.
- Read the smallest complete set of relevant files.
- Inspect tests before implementation.
- Build a short internal plan.
- Prefer targeted edits.

### During editing

- Keep a clear list of files changed.
- Run focused tests after each meaningful change.
- Do not repeatedly scan the whole repository.
- Do not generate large speculative patches.
- Do not mix unrelated tasks.
- Stop and reassess when tests fail for unexpected reasons.

### Before finishing

Run relevant checks.

Backend examples:

```bash
cd backend
uv run pytest tests/path/to/test_file.py -q
uv run pytest -n auto
uv run mypy .
uv run pre-commit run --all-files
```

Frontend examples:

```bash
cd frontend
npm run typecheck
npm run lint
npm run test
npm run build
```

Use the project’s actual scripts if they differ.

### Final response from a coding session

Summarize:

- files changed
- tests added
- behavior fixed
- tests run
- remaining risks
- follow-up work if needed

Do not overstate. If something was not run, say so.

## 16. Common Pitfalls to Avoid

Backend:

- accepting invalid workflow YAML at registration time
- compiler/runtime step-type drift
- storing `Step.error` as a string in one path and dict in another
- marking a run resumed without completing the suspended step
- failing a run while leaving the current step suspended/running
- retrying deterministic policy violations
- applying callback side effects twice
- letting unsafe tool calls execute after verifier/policy failure
- leaking secrets in audit or API responses
- assuming a test DB without enforced foreign keys (tests run on PostgreSQL; seed parent rows)
- mocking away the actual executor behavior
- tests that check only status codes

Frontend:

- stale React Query data after retry/resume
- live WebSocket overlay contradicting canonical DB state
- step-number mismatch after retry or resume
- showing old failed attempts as current failures
- not clearing running state after suspended/completed/failed events
- UI labels that do not match backend semantics
- helper tests without page-level wiring tests

Cross-cutting:

- changing backend API without frontend type updates
- changing YAML DSL without examples and compiler tests
- changing event names without stream/UI updates
- changing errors without API and frontend rendering tests
- changing prompts without runtime validation tests

## 17. Definition of Done

A change is done only when:

- relevant source paths were inspected
- code is minimal and scoped
- tests were added or updated
- negative paths are covered where relevant
- API/frontend contracts are updated together
- migrations are included when models change
- sensitive data is not exposed
- relevant tests pass
- commit messages are clean, concise, and free of AI attribution
- the final summary is honest about what was and was not verified
