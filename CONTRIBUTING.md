# Contributing to Saz

Thanks for taking the time to look at the code. Saz is a small project and
we keep contributions easy to review.

## Local setup

You will usually need both halves of the stack, plus a reachable **PostgreSQL**
database (Saz is PostgreSQL-only — set `DATABASE_URL` to a `postgresql+psycopg2://`
URL in `.env`):

```bash
# Backend
cd backend
uv sync
cp .env.example .env
uv run alembic upgrade head
uv run uvicorn saz.api.app:app --reload --port 8000

# Frontend (separate terminal)
cd frontend
npm ci
cp .env.local.example .env.local
npm run dev
```

Install the pre-commit hooks once per clone:

```bash
pre-commit install
```

Hooks live in the repo root (`.pre-commit-config.yaml`) and cover ruff,
ruff-format, mypy, uv-lock, and the frontend's typecheck / lint /
format:check.

## Branch and PR expectations

- Branch from `main`. Keep branches short-lived.
- One focused change per PR. Don't mix refactors with feature work.
- Open the PR against `main`. CI runs the `backend` and `frontend` jobs on
  path changes and aggregates them into a single required check
  (`CI / CI`). PRs must be green before merge.
- Update docs in the same PR when you change behavior, env vars, or
  commands.

## Tests

Every meaningful code change ships with tests in the same PR.

- For bug fixes, add a failing regression test first, then the fix.
- For new behavior, add success, validation-failure, and runtime-failure
  cases. Cover the negative paths (blocked tools, malformed input, late
  callbacks, suspension timeouts) where they apply.
- Backend: `cd backend && uv run pytest -n auto` (always `-n auto`). Tests run
  against PostgreSQL; each xdist worker creates its own isolated database from
  `TEST_DATABASE_URL` (see `backend/README.md`).
- Frontend: `cd frontend && npm run test`.

See `backend/README.md` for the test layout and assertion expectations.

## Commit messages

Use a short imperative subject, optionally with `<type>(<scope>)`:

```
fix(api): validate flow registration
test(engine): cover webhook reject state
feat(runs): expose retry attempt metadata
refactor(policy): simplify PII decision path
docs: update workflow testing guide
```

Rules:

- Imperative mood (`add`, `fix`, `remove`), not past tense.
- Keep the subject concise. Use the body only when context is needed.
- Don't include AI-tool attribution in commits, comments, or PR bodies
  (no "generated by …", "co-authored-by: <assistant>", etc.). The history
  should describe the engineering change.
- Avoid vague subjects like `update`, `fix stuff`, `changes`.

## PR description

Use the template in `.github/pull_request_template.md`. Keep it short:
summary, type of change, tests run, risk/rollback notes, screenshots when
UI changes.

## Code style

- Backend: ruff (`E`, `F`, `I`, `B`, `UP`, `W`), ruff-format, mypy strict
  flags as configured in `backend/pyproject.toml`.
- Frontend: ESLint (`next lint`) + Prettier. Run `npm run format` before
  pushing.
- Don't reformat unrelated files. Don't rename broad concepts without a
  reason.

## Scope discipline

Keep PRs reviewable:

- Don't add abstractions without a concrete need.
- Don't introduce hidden global state.
- Don't break the public API surface (`/api/v1/...` and the frontend
  types in `frontend/lib/types.ts`) without updating both sides.
- Migrations must match SQLAlchemy models and ship in the same PR.

## Reporting issues

Use GitHub Issues for bugs and feature requests. For security reports,
follow [`SECURITY.md`](SECURITY.md) instead.
